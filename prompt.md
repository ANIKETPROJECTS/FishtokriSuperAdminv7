# FTW Razorpay Orders: Always Persist Successful Payments as Paid

## Issue

Some storefront orders whose IDs start with `FTW` were created after a successful
Razorpay payment, but the MongoDB order document was saved with inconsistent
payment fields:

- `paymentStatus: "unpaid"`
- `paidAmount: 0`
- `dueAmount` equal to the full order total
- `payments: []`

At the same time, the same order contained a Razorpay transaction ID, for
example `upiTransactionId: "pay_..."`, and the order was displayed as UPI/RZPAY.
This caused the admin panel to show a paid online order as unpaid and due.

The admin panel is not the source of the FTW order document. FTW orders are
generated by the storefront application and arrive through the online/Razorpay
checkout flow. The admin panel can repair payment metadata, but the storefront
must persist the correct payment state at creation or in the successful payment
callback.

## Required storefront behavior

Whenever an `FTW...` order has a **successful Razorpay payment**, the storefront
must always save the order as fully paid, regardless of whether the delivery is
scheduled for:

- today;
- tomorrow;
- a later date;
- a current delivery slot; or
- a next-day delivery slot.

The delivery date, schedule type, and timeslot must never cause a successful
Razorpay order to be saved as unpaid.

This rule must be applied in both places:

1. when the FTW order document is initially created; and
2. in the Razorpay success/webhook/callback update that finalizes the payment.

## MongoDB fields for a successful FTW + Razorpay order

For a successful payment, persist the following values:

```js
{
  orderId: "#FTW...",
  source: "online",
  paymentMode: "upi",
  upiVariant: "RZPAY",
  paymentStatus: "paid",
  paidAmount: total,
  dueAmount: 0,
  payments: [
    {
      mode: "upi",
      amount: total,
      reference: razorpayPaymentId,
      paidAt: new Date()
    }
  ],
  upiTransactionId: razorpayPaymentId
}
```

Where:

- `total` is the final order total after discounts, coupons, wallet amounts,
  and delivery/slot charges;
- `razorpayPaymentId` is the actual successful Razorpay payment ID;
- `paymentStatus` must be exactly `"paid"`;
- `paidAmount` must equal the amount actually paid, normally the full `total`;
- `dueAmount` must be `0` for a fully paid order.

Do not leave `payments` empty when a successful Razorpay payment ID exists.
Do not use the delivery date or slot date to decide whether the payment is
paid.

## Important safety rule

Only successful Razorpay payments should be marked paid. Failed, cancelled,
expired, or still-pending Razorpay payments must remain unpaid or pending
according to the storefront's payment-state model.

The decisive condition is a verified successful Razorpay result, such as a
verified payment callback/webhook or a confirmed successful payment response,
not merely the presence of an order ID.

## Regression checks

Before shipping the storefront fix, verify all of these cases:

- FTW order with delivery today + successful Razorpay payment → `paid`;
- FTW order with delivery tomorrow + successful Razorpay payment → `paid`;
- FTW order with a later delivery date + successful Razorpay payment → `paid`;
- FTW order with a current slot + successful Razorpay payment → `paid`;
- FTW order with a next-day slot + successful Razorpay payment → `paid`;
- failed Razorpay payment → not marked paid;
- pending Razorpay payment → not marked paid;
- successful payment callback received after order creation → updates the
  existing FTW document to `paid`, sets `paidAmount`, clears `dueAmount`, and
  writes the payment entry;
- retrying the callback is idempotent and does not duplicate payment entries.

## Admin-panel observation

The admin panel previously repaired FTW metadata by setting:

```js
{
  paymentMode: "upi",
  upiVariant: "RZPAY"
}
```

That repair did not itself create the original unpaid state. The permanent fix
belongs in the storefront FTW order creation and Razorpay success handling.
